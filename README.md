# Go Messenger — готовый учебный MVP

**Сервер:** Go, WebSocket, PostgreSQL. **Клиент:** HTML/CSS/JavaScript. **Язык интерфейса:** русский.

## Возможности

- Регистрация (Argon2id), вход, выход и сохранённая сессия на 7 дней через HttpOnly cookie.
- Общий чат с историей (до 50 последних сообщений) и онлайн-доставкой.
- Личные диалоги между зарегистрированными пользователями; сообщения отправляются только участникам переписки.
- Индикаторы онлайн, набора текста, повторное соединение WebSocket.
- Адаптивный интерфейс, синий сердечко-кнопка, меняющая цвет на розовый при наведении.
- Запуск через Docker Compose, сохранение данных в томе PostgreSQL; конфигурация Caddy + HTTPS для VPS.
- Сохранена **совместимость таблиц** `messages`, `users`, `sessions` из этапов обучения. При старте приложение добавляет `sender_id` в `messages` и создаёт `direct_messages`.

**Ограничения:** это MVP, **не Telegram** и **не сквозное шифрование**. Сервер и администратор БД потенциально могут видеть сообщения. Нет файлов, звонков, push-уведомлений, восстановления паролей, полноценного мониторинга и горизонтального масштабирования. Перед публичным запуском с реальными пользователями сделайте аудит безопасности, резервное копирование и нагрузочное тестирование.

## 1. Самый простой запуск на Windows (Docker Desktop)

1. Сохраните резервную копию текущего проекта, включая `web/index.html` (ваш собственный дизайн).
2. Если старый сервер Go занимает `8080`, остановите его через `Ctrl+C` в старом терминале VS Code. Проверка в PowerShell: `Get-NetTCPConnection -LocalPort 8080 -State Listen`.
3. Убедитесь, что Docker Desktop показывает `Engine running`.
4. Распакуйте архив. Перейдите в каталог проекта, где лежит `compose.yaml`.
5. Выполните:

```bash
docker compose up -d --build
docker compose ps
```

6. Откройте **http://localhost:8080**. При первом запуске образ Go загрузит зависимости из Интернета.
7. Зарегистрируйтесь или войдите под **старым** `alex123` и прежним паролем, если вы сохранили том от предыдущего проекта.

**У вас уже есть локальная БД?** `compose.yaml` использует `name: go-messenger`, сервис `db` и том `postgres_data`, поэтому при обычном расположении старого проекта Docker повторно использует прежний том `go-messenger_postgres_data`. При сохранении базы `users`, `sessions` и общие сообщения не стираются. Если раньше было другое имя проекта Compose, потребуется отдельное восстановление из резервной копии. **Не запускайте `docker compose down -v`**: эта команда удаляет том с перепиской!

Локальная конфигурация использует прежний пароль БД `messenger_dev`. Не размещайте порт PostgreSQL в открытом Интернете. Снаружи localhost контейнер БД недоступен.

### Логи и остановка

```bash
docker compose logs -f app
docker compose stop
docker compose start
```

При изменении кода:

```bash
docker compose up -d --build
```

### Сделать резервную копию БД перед обновлением

В каталоге **старого** проекта, пока его PostgreSQL запущен:

```bash
docker compose exec db sh -c 'pg_dump -U messenger -d messenger -Fc > /tmp/messenger.backup'
docker compose cp db:/tmp/messenger.backup ./messenger.backup
```

Проверьте, что `messenger.backup` появился на диске; храните его в безопасном месте. Изображения и видео эта версия не хранит.

## 2. Запуск напрямую через Go (без контейнера приложения)

Требуется **Go 1.25+**, PostgreSQL, и база из `compose.yaml`:

```bash
docker compose up -d db
go mod tidy
```

Bash / Git Bash:

```bash
export DATABASE_URL='postgres://messenger:messenger_dev@127.0.0.1:5432/messenger?sslmode=disable'
go run ./cmd/server
```

PowerShell:

```powershell
$env:DATABASE_URL='postgres://messenger:messenger_dev@127.0.0.1:5432/messenger?sslmode=disable'
go run ./cmd/server
```

Проверка: **http://localhost:8080/healthz**. Если получаете ошибку `bind` на `8080`, остановите старый Go-сервер или контейнер `app`, который уже использует порт. Для работы напрямую через Go в каталоге проекта должна быть папка `web`.

## 3. Публикация на VPS с доменом и HTTPS

Нужен Linux VPS с публичным IP, установленными Docker Engine/Compose, домен (например, `chat.example.com`) и доступ к DNS.

1. Создайте **A-запись** домена, указывающую на IP сервера; для IPv6 можно добавить AAAA-запись.
2. Разрешите входящие **TCP 80 и 443** (а также UDP 443, если нужен HTTP/3). Базу `5432` наружу не открывайте.
3. Передайте папку проекта на VPS (Git, SCP/SFTP), откройте терминал в каталоге проекта.
4. Скопируйте `.env.production.example` в `.env.production`. Укажите реальный домен и случайный пароль из `openssl rand -hex 24`; не публикуйте этот файл и не добавляйте в Git.
5. Запустите:

```bash
docker compose --env-file .env.production -f compose.prod.yaml up -d --build
docker compose --env-file .env.production -f compose.prod.yaml ps
docker compose --env-file .env.production -f compose.prod.yaml logs -f caddy
```

6. Откройте **https://ваш-домен**. Caddy автоматически получает и обновляет сертификат, если DNS и порты настроены правильно. В production cookie помечается `Secure: true`.
7. Настройте периодическое резервное копирование БД и обновления контейнеров; проверьте безопасность VPS и ограничение попыток входа. Приложение предназначено для одного экземпляра сервера.

Конфигурация Caddy — `deploy/Caddyfile`. **Не публикуйте production без HTTPS**. Приложение внутри Docker использует `http://app:8080`, но снаружи Caddy обслуживает HTTPS.

**Перенос старых сообщений на VPS:** том локального Docker не копируется автоматически. Сначала снимите резервную копию через `pg_dump` (выше), перенесите её на VPS, остановите `app` и восстановите через `pg_restore` в пустую базу с совпадающим паролем; затем снова запустите `app`. Это отдельная административная операция, перед выполнением которой сохраните копию данных VPS.

## 4. Проверка

```bash
go mod tidy
go test ./...
go vet ./...
```

После запуска: создайте два аккаунта в разных браузерах (или один в приватном окне), откройте «Общий чат», затем личный диалог. Проверьте, что сообщения не пропадают после `Ctrl+R` и что после выхода открытие `/api/me` возвращает `401`.

## 5. Безопасность и схема

- `POST /api/register` — создать пользователя и сессию.
- `POST /api/login` — вход и создание новой сессии.
- `POST /api/logout` — удалить текущую сессию на сервере и cookie.
- `GET /api/me` — узнать пользователя из сессии; `401`, если она недействительна.
- `GET /api/users` — список других пользователей (только после входа).
- `GET /api/messages` — история общей комнаты (после входа).
- `GET /api/messages?peer_id=2` — личная история двух участников (после входа).
- `GET /ws` — WebSocket с проверкой cookie и Origin.

Хеш пароля — Argon2id, параметры совпадают со старым обучающим проектом. Хеш токена сессии — SHA-256; сырые токены не сохраняются в БД. Новые сообщения получают отправителя из сессии, а не из присланного клиентом имени. Для отправки используется WebSocket, для истории — HTTP API. Отменённая/истёкшая сессия не позволяет отправлять новые события по WebSocket. Есть базовое ограничение попыток регистрации и входа **на один адрес TCP**; за одним прокси все посетители делят квоту. Для серьёзной публичной эксплуатации нужен отдельный rate-limiter с доверенной настройкой reverse proxy, аудит CSRF/XSS/CSP и наблюдаемость.

Веб-интерфейс использует `textContent` для текста сообщений, чтобы не исполнять HTML от других пользователей. Архитектура — один экземпляр Go-сервера и один PostgreSQL.

## 6. Что нужно знать перед заменой старого проекта

В архив включена **новая реализация**, созданная по истории нашей переписки и предыдущему учебному каркасу. Это не побайтовая копия файлов, которые сейчас лежат на вашем ПК: прямого доступа к локальному диску нет. Не копируйте поверх старого проекта до бэкапа. Таблицы `messages` и `users` предполагаются в том виде, который мы создали ранее: `messages(username, content, created_at)` и `users(username, password_hash, created_at)`. Остальная история автоматически сохраняется при нормальной миграции.
